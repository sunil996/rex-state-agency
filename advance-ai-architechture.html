One-line summary

Turn your raw data (warehouse tables) + scattered knowledge (wiki, code, query history) into a curated, machine-checkable folder of markdown — one folder per business “domain” — that an AI agent reads (router → domain → playbook → SQL) to answer questions correctly, plus skills that let agents build and maintain that folder, plus a gate that keeps it honest.

1. What we are building & why

The problem

Without a knowledge layer, an LLM agent asked “what’s our decline rate last week?” will:

  • guess the table and column names (hallucination),
  • forget mandatory filters (partition, test traffic, shadow mode),
  • join on the wrong key or wrong grain (double-counting),
  • misread types (STRING “0/1” vs BOOL, cents vs dollars, -999 sentinels),
  • use a stale or derived view instead of the source of truth.

With a knowledge layer, the agent:

  • routes the question to the right domain (SKILL.md router),
  • reads verified column meanings and “type traps” (dictionaries),
  • starts from a vetted, parameterized SQL recipe (playbooks),
  • applies the domain’s guardrails and join rules,
  • cites where each fact came from (sources:).

Design principles (keep these in any port)

  1. Knowledge-centric, not view-centric. Document raw (root) tables; keep derived logic as copy-paste SQL in a playbook, not as deployed views.
  2. Every claim is grounded. Schema from the warehouse, logic from real code, meaning from the wiki. Precedence decides conflicts.
  3. Machine-checkable. Every doc carries frontmatter; navigation is generated, never hand-maintained.
  4. Progressive disclosure. Router → domain → one playbook → only the dictionaries needed. Small context per question.
  5. Human-in-the-loop. Agents draft; humans approve. Human corrections are recorded so AI never silently regresses them.
  6. Record dead-ends. If something can’t be curated (no table, no access) write down why, so nobody re-investigates.

3. Sources of truth & precedence

Three sources, three jobs. When they disagree, the higher one wins and the loser is corrected and cites the winner.

1. Live warehouse schema
(INFORMATION_SCHEMA) — authority for columns, types, existence
▼ beats
2. Validated code
(external_sources/) — authority for how metrics / joins / filters are really computed
▼ beats
3. Wiki / tickets via MCP
— authority for business meaning, why a rule exists
▼ beats
4. Query-log / session evidence
— corroboration only, never authority
▼ beats
5. Existing corpus (often AI-written)
— lowest trust; cross-check only
Real example of why this matters

Curated prose said login ↔ payment joins on cal_corr_id. A validated production pipeline in external_sources joined on global_sn_id. Code beat prose → the corpus was corrected and now cites external:sql-001.

6. How to decide domains

Definition

A domain is a self-contained decision point, business process or analytical subject that has its own primary table(s) and its own set of questions. It is not “one table” — a domain owns one primary table plus every secondary table its playbooks need (each with its own dictionary).

6.1 Decision flow for each candidate

Start: a candidate (checkpoint / service / process / dataset / metric family)
▼
Q1 Is there at least one queryable table in your warehouse that records it?
NO →
do NOT curate. Leave a <name>_p scaffold (or nothing) and record why (no table / access denied / retired / empty) + a recheck recipe.
YES ↓
proceed to Q2
▼
Q2 Is it live? (latest partition recent, non-empty)
NO →
mark retired/historical, record, skip.
YES ↓
proceed to Q3
▼
Q3 Does it have its own decision semantics / questions, distinct from an existing domain?
NO →
it’s a topic: add a playbook/lens to the existing domain (/curate-topic), or a row in global_concept_registry.md, or acronyms/.
YES ↓
proceed to Q4
▼
Q4 Does it span several domains with no table of its own?
YES →
put it in cross_domain_playbooks/ (orchestration runbook), not a domain.
NO →
create a DOMAIN /curate-domain <name>

6.2 How many domains will I have?

  1. Inventory decision points. List every service / checkpoint / pipeline stage / business process (from architecture docs, service registry, event-log catalog). Reference impl: listed every risk checkpoint (login, signup, funding, withdrawal, dispute…).
  2. Inventory tables. INFORMATION_SCHEMA.TABLES per dataset; group by naming prefix / producer.
  3. Map decision point ↔ primary table. Unmapped decision points = scaffolds/dead-ends; unmapped big tables = candidate dataset domains (e.g. “unified dataset”, “account profile probe”).
  4. Add analytical-subject domains that aren’t a single service: entity probes (account / merchant profile), rule engine metadata, BI aggregates platform, outcome/label datasets (loss, disputes).
  5. Count: domains ≈ (live decision points with a table) + (dataset/subject domains). Expect 5–15 for a small product, 50–150 for a large platform. Start with the 3–5 most-asked.

6.3 Split vs merge rules

SPLIT into separate domains when…

  • different grain (per-case vs per-transition, e.g. dispute initiation vs adjudication),
  • different owning service / decision,
  • different tenants that must never be blended (e.g. PayPal vs Venmo),
  • the playbook sets barely overlap.

MERGE / keep in one domain when…

  • tables are siblings of the same decision (batch vs near-real-time copy),
  • a table is only a lookup/dimension for that domain,
  • a “domain” would have <2 meaningful playbooks — make it a lens/playbook instead.
Naming conventions
  • Directory = snake_case of the business name; frontmatter domain: must equal the directory name.
  • _p suffix = un-curated scaffold. On curation, rename to drop _p.
  • Non-domain dirs are declared in code: NON_DOMAIN_DIRS = {scripts, templates, diagrams, .git, .claude}.

Why kt_resolve matters at scale

Give it a SQL query → it returns only the home dictionaries + grains + join keys for the tables that query touches (a dozen lines). The agent never loads 200 dictionaries — context scales with the question, not the corpus.

Universal query safety rules (put these in the root SKILL.md)

  1. State the grain before and after each join; aggregate the N-side before joining.
  2. Partition filter on every large table and every CTE (filters don't push into CTEs).
  3. COUNT DISTINCT for rates after joins.
  4. Pre-filter the right side of a LEFT JOIN in a CTE (WHERE on it turns it into INNER).
  5. Check the dictionary's Type Traps before CAST/SUM/AVG.
  6. Confirm the join key exists on both sides + its cardinality (join_topology).
  7. Decide NULL semantics for every != / NOT IN.
  8. SAFE_CAST log/signal fields.
  9. Explicit TIMESTAMP↔DATE conversion. SAFE_DIVIDE. UNNEST inflates grain. per-section LIMIT in UNION ALL.
  10. Analyze result CSVs locally with DuckDB SQL, pandas only for plotting.

19.5 LLM-readable authoring rules REC

  • Front-load: the first 10 lines of every doc say what it is, its grain, and when to use it or not.
  • Size budget: keep SKILL.md small (aim for under ~300 lines). Split big dictionaries into a core file and a full-registry file (the reference does this for UDS). One playbook = one question family.
  • Explicit negatives: “NOT the funding decision — see X”. These state what a doc does not cover, and they stop mis-routing.
  • Stable headings: ## Guardrails, ## Template T1 so agents and graders can address sections.
  • Copy-runnable SQL: fully qualified tables, named parameters, partition filter already present.
  • Numbers with dates: “710 cols (verified 2026-10-06)”. Unverified claims are marked UNVERIFIED.
  • One fact, one home: link to the fact instead of copying it (join keys live in dictionary joins:; not repeated in prose).

# Create a table Dictionary

## Non-negotiable rules
1. Types and column list come from INFORMATION_SCHEMA. Never hand-type them.
2. Low-cardinality categorical (roughly ≤ 50 distinct, or a code/enum/flag/status) →
   list EVERY observed value + every code-defined value, each with a meaning.
3. High-cardinality (ids, account numbers, emails, phones, hashes, timestamps, amounts,
   scores, free text) → 2-3 samples only. Never enumerate PII.
4. Meaning sources, in order: validated code (enum definitions, CASE logic) → wiki →
   leave "meaning unknown" needs owner (never invent).
5. One table = one dictionary = one `resource`. If the table is already homed elsewhere,
   extend that dictionary instead of creating a second home.
6. Bounded profiling: always filter the partition column and sample; cap bytes.

# Curate a domain

## Non-negotiable rules
1. Discover meaning (wiki/MCP) and logic (validated code) IN PARALLEL. Existing docs are
   cross-check only.
2. Precedence: live schema > validated code > wiki > existing corpus. The loser is
   corrected and cites the winner.
3. Every table any playbook reads gets a dictionary via /create-dictionary.
4. Playbooks read RQT tables only. Derived logic goes in <domain>_derived_flags.md.
5. Human reviews before merge. Surface uncertainty; never guess join keys.
6. Gate must be warning-clean for this domain: KT_STRICT=1 kt_check.sh --domain <d>.
7. If no queryable live table exists: STOP. Record a dead-end note (what it is, why
   blocked, how to recheck). Leave the _p scaffold.

## Phase 0 - Discover (parallel)

decides, its outcomes, which tables it cannot read, issues. Record ids.
Agent B (code): index.py search "<name>" - context. Capture real joins, filters, metric
formulas, dedup logic, the tables the code actually reads. Record external ids.
